## Position

Delivery latency is tracked on the coordinator's clock. 4f205f0 landed on main by CAS from d9f0109, and the primary checkout (`claude-parity`) was fast-forwarded to it. Both hosts run the core deployed from 4f205f0 (sha256 e93779fe…). Mail is unchanged: the frozen glossary defines it as id, sender, recipient and body, so the stamps live in the coordinator's log events and in the Receipt.

- `src/coordinator.rs`:
  - The `mail` and `broadcast` events carry `accepted_at_ms`. Each Broadcast copy takes its broadcast's stamp.
  - The `receipt` event carries `receipted_at_ms`. Both stamps are read from the coordinator's `now_ms`.
  - The send, ack and broadcast paths now go through `commit`, the same as the other events.
  - A new `receipt` request answers with `to`, `accepted_at_ms`, `record` and `receipted_at_ms`. A stamp the log never held is left out, never sent as 0.
- `src/daemon.rs` relays `receipt` the way it relays `claim` and `board`.
- `roger receipt --socket --mail <id>` prints `RECEIPT mail= to= record= accepted_at_ms= receipted_at_ms= latency_ms=`, or `PENDING mail= to= accepted_at_ms=`, and prints `absent` for a missing stamp.
- Store entries add `stored_at_ms` and `clock` (`/proc/sys/kernel/hostname`; agent-jail reports `JangsJail`).
- GLOSSARY `## Language` gains Accepted at, Receipted at and Stored at.
- README gains `## Receipts and latency`.
- `scripts/acceptance cross-host` now requires both stamps on `accept-1` and prints the RECEIPT line.
- No shim changed. Neither shim reads the Store, the adapter's `mail` line is unchanged, and the Tracer's `STORED` line is unchanged (broadcast acceptance anchors `wake=false$`).
- Surface chosen: one read request plus one client subcommand. The Receipt arrives after the sender's send has returned, and only the coordinator holds both stamps, so a read by Mail id is the only way a sender can see them. Putting them on `accepted` or the recipient's `acked` answer would add fields on two paths and still miss the Receipt for the sender.

## Tried

- The late-receipt risk from `VECTORS/no-poll/20261022-071911.md` was reproduced at d9f0109 with the release-free debug build (`/tmp/rwstall`). The coordinator was SIGSTOPped, the recipient acked, and the daemon logged `upstream forward deferred: upstream did not answer` after 10 s. The receipt row appeared within 0.5 s of SIGCONT, with no reconnect. The forward is already on the TCP link, so the coordinator commits it when it reads it, and its late `acked` trims the daemon's replay list (`upstream_once`). The receipt is held until a reconnect only when the link actually drops, or when the coordinator refuses an unknown mail (`receipt_survives_an_upstream_that_never_accepted_the_mail`).
